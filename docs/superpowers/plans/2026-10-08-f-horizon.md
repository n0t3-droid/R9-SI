## What F8 has to deliver (spec, condensed)

1. No pops: new near chunks fade in over 300 ms; LOD tiles crossfade with the chunks that replace them through a soft mask edge; no holes.
2. Horizon colours equal the near terrain: same tints/albedo averages, same fog and aerial-perspective hook (applyFog, env values).
3. Streaming budget: N ms of uploads per frame (measured), meshing never blocks, priority by view direction; frame-time pressure lowers the streaming rate first, resolution second, the view distance never.
4. Impostors (trees, villages beyond renderDist), village lights as points at night, far rings merging flat areas.
5. Cost: 3 km horizon under 2 ms CPU per frame and under 40 MB on balanced; 1 km under 2 ms on Very Low.
6. Coarse hierarchical occlusion for near chunks behind big hills, LOD heightfield as occluder.
7. Tests: node tests for the soft mask edge and the streaming scheduler (never over budget, priority order); browser test/horizon.mjs (20 s flight at 3 km, frame times logged, no frame above 2x the median from streaming, a screenshot every 2 s checked for sky-coloured pixels below the horizon line; 3 km vistas on Very Low and High in test/shots/horizon_*.png).

## Code facts that shape the design (read before coding)

- The chunk terrain (TERRAIN_VS / TERRAIN_FS / TRANS_FS, renderer.js P.opaque, P.cutout, P.trans) shares its vertex shader with the ship programs; per-draw origins come from the std140 block `Origins` (vec4 per draw, w unused = 0) in the multi-draw path and from the `u_origin` vec3 otherwise. The ship programs must keep full opacity, so the fade is opt-in through a `FADE` define on the three world programs.
- LOD tiles (horizon.js, shaders.js LOD_FS) are cut where chunks are drawn by a 64x64 R8 mask (NEAREST, `> 0.5`), i.e. a hard edge and a pop when a chunk arrives.
- Fog is one function, applyFog (shaders.js COMMON), used by terrain and LOD alike; the LOD albedo comes from the same atlas average (bcol / avgColor). The colour contract is therefore kept by sharing applyFog and the atlas averages; the remaining difference is shading (no shadow map, no per-vertex AO on tiles) and is measured, not hidden.
- Mesh results are uploaded synchronously in the worker callback (world.js meshSection → renderer.uploadSection). A per-frame upload budget needs a queue there.
- game.js smartQuality (aq) climbs a GPU ladder and a CPU ladder that currently drop renderDist (rd rungs) and the far horizon (hz rung). The spec forbids both. The fix: those rungs go; streaming-rate rungs go first in the CPU ladder; resolution stays in the GPU ladder.
- test/load_shared.js loads the shared modules for node tests from a fixed list; the new module is added to that list and to build.js SHARED.

## Design

### A. src/shared/stream.js (pure, node-testable), namespace VR.Stream
- `fadeCurve(t)`: smoothstep of t = elapsed / 300 ms, clamped to 0..1.
- `bayer4(x, y)`: 4x4 ordered-dither threshold in [0, 15/16] (the same closed form as the shader's bayer4).
- `chunkKeeps(fade, x, y)`: the chunk fragment at pixel (x, y) is drawn iff bayer4 < fade.
- `lodCover(nearestFade, bilinearFade)`: min(bilinear, nearest). The LOD fragment is cut iff bayer4 < cover.
  Invariant (tested): cover <= nearest fade, so for every pixel and threshold, the chunk draws or the LOD draws (no hole); overlap is possible and resolved by depth.
- `bilinear(texels, u, v)`: the same bilinear filter the GPU applies to the 64x64 mask (texel centres at (i + 0.5) / 64). Used by the test to check the soft band is at least one chunk wide.
- `UploadScheduler`: a queue of { cost estimate bytes, run(), prio } items. `drain(budgetMs, clock, dirX, dirZ)` orders items by `viewPrio` (distance times a factor that is 1.0 straight ahead and 2.2 straight behind) and runs them while spent + estimate <= budget; the estimate is an EMA of measured ms per byte. Items never start past the budget; a single item larger than the whole budget waits until the budget is raised (the pressure rule never lowers it below one small section, so nothing starves). Test: spent <= budget with an accurate estimate, order by viewPrio, pending items keep their order.
- `pressureRung(frameMs, target, rung)`: the streaming rate steps 1 → 0.5 → 0.25 when the frame is slow and back up when it is fine (hysteresis in the caller, game.js aq). View distance is not an input.

### B. Chunk fade-in (300 ms, dithered, no blending)
- world.js: a column is shown when all 16 sections are meshed for the first time; its sections get `s.fade = 0` until then (so partially meshed columns stay hidden, the LOD stays under them) and `c.shownAt = now`; `this.fading` holds the columns still fading; each world.update sets `s.fade = fadeCurve(...)` for them and removes them at 1.
- renderer.js drawSections: origin w = s.fade (1 for non-world sections); sections with fade 0 are skipped (they are invisible and must not cast shadows); the non-multi path sets `u_fade`.
- shaders.js TERRAIN_VS / TRANS_FS: under `#ifdef FADE` read the fade (`u_origins[gl_DrawID].w` or `u_fade`), pass a flat varying, and discard with bayer4 >= fade in the fragment shaders. Ship programs do not define FADE and are unchanged.

### C. Soft LOD mask
- horizon.js updateMask: per frame while any column fades (throttled otherwise), texel = column fade (0..255), LINEAR filter.
- LOD_FS: `cover = min(texture(u_mask, uv).r, texelFetch(u_mask, ch, 0).r)`; `if (bayer4(gl_FragCoord.xy) < cover) discard`. This replaces the hard `> 0.5` cut; a column that is not shown keeps cover 0.

### D. Streaming budget
- world.js: mesh results go into `this.uploadQ` (a UploadScheduler) instead of an immediate `uploadSection`; `world.update` drains it with `budgetMs` = preset base x rung (potato 1.5, low 2, balanced 2.5, high 3, ultra 3) — the number is measured per frame (`stats.uploadMs`).
- Columns are shown only after their upload completes, so the draw-order stays consistent.

### E. Governor (game.js)
- Remove the rd (renderDist) and hz (horizon level) rungs from aqGpuRungs and aqCpuRungs.
- CPU ladder starts with the streaming rungs (o.stream = 1, then 2).
- Resolution remains in the GPU ladder (scale).

### F. Horizon cost
- horizon.js: `stats.cpuMs` (update + draw, performance.now), `stats.mb`, `stats.tris` kept.
- Tile selection is already O(tiles visited); the draw loop already culls by frustum. Measured first, then optimised only where the numbers say so.

### G. Not in this session unless the numbers allow (named gaps)
- Impostor billboards for trees and villages beyond renderDist (cross-faded with real chunks).
- Village lights as night points.
- Hierarchical occlusion behind hills (LOD heightfield as occluder).

## How it is measured

- Browser: headless Chromium with SwiftShader (CPU), so absolute times mean little; relative costs do.
- Fixed scene: world seed 1, noon (env time 6000), zen freeze, 1280x720, the player at the spawn point of seed 1, horizon level 3 (3 km) for the 3 km numbers and level 1 (1 km) for the Very Low 1 km number.
- Presets: Very Low = potato, High = high.
- Numbers per run: renderer.stats (draws, tris), horizon.stats (drawn tiles, tris, MB, cpuMs), render frame ms (performance.now around g.loop), uploadMs (new).
- Before = the untouched v041 code (baseline run, numbers in the section below); after = this branch.
- Probe for holes: a sky-probe uniform paints the sky magenta for one frame; a pixel below the horizon row that is magenta is a hole (readPixels right after the frame).
